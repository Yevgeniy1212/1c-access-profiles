# access-profile-check

Проверка профилей «на здоровье». Ничего не меняет.

## Шаги

1. Проверить `.roles-access.yaml`. Нет — `/access-init`, остановиться.
2. Выполнить:

   ```
   python .cursor/1c-access-profiles/scripts/profile_check.py --all
   ```

   Один профиль: `python .cursor/1c-access-profiles/scripts/profile_check.py --profile "<имя>"`

3. Показать таблицу замечаний и объяснить каждое простыми словами.

## Что означают коды

| Код | Что значит | Почему важно |
|---|---|---|
| `EMPTY_PROFILE` | в профиле нет ролей | пользователь с таким профилем не увидит ничего |
| `ROLE_MISSING` | роль указана, но её нет в базе | обычно после обновления конфигурации роль переименовали; часть прав молча пропала |
| `DUPLICATE_ROLE` | роль включена дважды | безвредно, но засоряет профиль |
| `NO_LAUNCH_ROLE` | нет роли запуска клиента | пользователь не сможет войти в программу |
| `RLS_BYPASSED` | см. примечание ниже | ограничение доступа к данным не сработает |

## Важное ограничение проверки RLS

Тексты ограничений (`restrictionByCondition`) платформа через MCP **не отдаёт**:
свойство `Роль.Права` в рантайме недоступно. Поэтому полную проверку «ограничение
обходится другой ролью» автоматически выполнить нельзя.

Что делать вместо этого:
1. Проверить ограничения вручную в Конфигураторе (роль → «Ограничения»).
2. Либо воспользоваться отчётом «Анализ доступов к объектам» из конфигурации,
   если он есть (перечёркнутая роль = ограничение не действует).
3. Если ограничения нет ни у одной роли профиля — доступа «ко всем данным»
   не будет только по той причине, что роль вообще не даёт прав на объект.

## Запреты

- Не изменять данные.
- Не писать «RLS в порядке», если проверка не выполнялась.
