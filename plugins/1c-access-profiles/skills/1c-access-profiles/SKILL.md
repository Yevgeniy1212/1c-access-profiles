# Профили доступа 1С

Плагин для работы с **профилями и группами доступа** действующей базы 1С.
Роли берутся такими, какие они есть в конфигурации.

## Что умеет

| Команда | Что делает |
|---|---|
| `/access-init` | настраивает подключение, создаёт `.roles-access.yaml` |
| `/access-profiles-list` | список профилей с числом ролей |
| `/access-profile-show` | состав профиля: роли, виды доступа, ограничения |
| `/access-profile-analyze` | какие объекты даёт профиль и на каком уровне |
| `/access-profile-compare` | отличие двух профилей по ролям и объектам |
| `/access-profile-check` | типовые проблемы профилей |
| `/access-profile-builder` | создать профиль копированием существующего |

## Модель данных

```
ПрофильГруппДоступа (справочник)
  ├─ Наименование
  ├─ Роли            → ИдентификаторыОбъектовМетаданных (роли конфигурации)
  ├─ ВидыДоступа     → по чему ограничивать (Организации, Склады, ...)
  ├─ ЗначенияДоступа → конкретные разрешённые значения
  └─ Назначение      → типы пользователей

ГруппыДоступа (справочник)
  ├─ Профиль         → ссылка на профиль
  └─ Пользователи    → кто получает доступ
```

Профиль отвечает на вопрос «что можно», группа — «кому».

## Как определить, что даёт профиль

Профиль хранит **роли**, а не объекты. Прямой связи «роль → объекты» в базе нет,
поэтому уровень доступа вычисляется по факту:

```
ПравоДоступа("<право>", <объект>, <роль>) = Да
```

Правило вычисления уровня:
- `Добавление` или `Изменение` = Да → **изменение**
- иначе `Чтение` / `Просмотр` / `Использование` = Да → **чтение**
- иначе — доступа нет

Это делает `scripts/profile_analyze.py`.

## Сопоставление ролей

Профиль ссылается на `ИдентификаторыОбъектовМетаданных`, их представление
выглядит как `"<Синоним роли> (Роль)"`. **Имя роли из синонима не выводится.**

Пример из практики: синоним `(киб) Использование обработки Расчет MRP`
соответствует роли `киб_ИспользованиеРасчетMRP` — без «Обработки».

Поэтому скрипт сначала читает все роли базы (`Имя|Синоним`), затем сопоставляет
синонимы профиля с этим списком. Если хоть одна роль не сопоставилась — анализ
останавливается (иначе часть прав молча потеряется).

## Что важно помнить

1. **Роли не создаются.** Если нужной роли нет — это задача разработчика
   в Конфигураторе, а не плагина.
2. **RLS через MCP не читается.** Тексты ограничений в рантайме недоступны;
   проверка обхода ограничений — ручная либо через отчёт конфигурации.
3. **Права по видам объектов различаются** — см. `rules/02-mcp-toolkit.mdc` §4.
4. **Запись только с согласия** — скрипты по умолчанию работают в режиме проверки.
5. **Поставляемые профили не правим** — изменения исчезнут при обновлении.
